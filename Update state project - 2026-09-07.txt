  x64 layout audit:
    sizeof(cGlobalPad) = 32
    sizeof(cPlatPad)   = 32
    sizeof(PadMonkey)  = 232

  Important:
    Retail hard-coded allocation sizes were 0x1C for cPlatPad and
    0xD8 for PadMonkey. Those are too small for the MSVC x64 layouts,
    so TARGET_PC now allocates with sizeof(...) while GameCube keeps
    the original retail constants.

  Deferred intentionally:
    SISetSamplingRate(0)
    PADSetSamplingCallback(VBlankPadUpdate)

    Aurora does not expose those retail APIs directly. The PC polling
    model will be decided only after the native frame loop is inspected.
    VBlankPadUpdate() must not be wired blindly.

  Controller validation:
    Real end-to-end polling/input validation is still pending.
    A PS4 controller will be connected when that stage is reached.

High-level interpretation — 07.09.2026

  Project LUDUS remains beyond the platform-proof stage.

  The native PC executable has a stable Aurora/WebGPU foundation,
  retail filesystem/config startup, global texture metadata loading,
  core managers, audio-startup validation, and now a real PC input
  runtime built from the retail globalpad / platpad / PadActions /
  PadMonkey code path.

  allocation constants are preserved for GameCube, while TARGET_PC
  allocates the larger MSVC x64 object layouts safely.

  InitPads() is now in the real PC startup sequence immediately after
  glInventory.Create(). Compile/link validation is green and the
  GameCube reference remains byte-valid at the established baseline.

  The immediate next checkpoint is deliberately small:
    runtime-smoke the executable with InitPads() active.

  sampling callback blindly, but to inspect the native frame loop and
  decide where Aurora PAD polling / VBlankPadUpdate() belongs.

  converting/uploading the real GameCube texture/render payloads into
  the native WebGPU path and continuing the retail startup chain far
  enough to produce the first genuine rendered game frame.
