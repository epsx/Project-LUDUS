x64 layout audit:

  sizeof(cGlobalPad) = 32
  sizeof(cPlatPad)   = 32
  sizeof(PadMonkey)  = 232


Important:

  Retail hard-coded allocation sizes were:
    cPlatPad   0x1C
    PadMonkey  0xD8

  Those are too small for the MSVC x64 layouts.

  TARGET_PC therefore allocates with sizeof(...), while GameCube keeps
  the original retail constants.

  PADSetSamplingCallback model.

  The PC port therefore does not fake those APIs.

  VBlankPadUpdate() is called explicitly once per native frame before
  nlTaskManager::RunAllTasks().

WorldUpdate remains intentionally deferred.

Retail behavior:

  if current state == 1 and FE state != start screen:
      WorldManager::UpdateWorld(0.f)
  else:
      WorldManager::UpdateWorld(dt)

State mask:
  0x20013

Contains:
  0x20000
  0x10
  0x2
  0x1

Does NOT contain:
  0x4

Critical lifecycle conclusion:

  Retail TransitionTask prepares the world before WorldUpdate becomes
  meaningful in state 2.

  The PC startup currently stages:
    skipfe ? 2 : 4

  but does not yet reproduce the full TransitionTask/world-loader lifecycle.

  Therefore:
    DO NOT add null guards merely to hide missing lifecycle ownership.
    DO NOT integrate WorldUpdate into production prematurely.
